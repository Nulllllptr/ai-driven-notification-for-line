# 実装ルール

このファイルはプロジェクトの実装規約を記録する生きたドキュメント。テンプレートの時点では未確定でよい。
実装を進めるたびに、決まった規約をここに追記していく。空欄のまま放置しない。

## 1. 命名規則
- 言語: Python、PEP8準拠
- 関数・変数・ファイル名: snake_case / クラス名: PascalCase / 定数: UPPER_SNAKE_CASE
- コンポーネント1つにつきモジュール1つを対応させる。モジュール名は仕様書のコンポーネント名を
  英語化したもの(例: 101ニュース収集 → `src/news_collector.py`)

## 2. 層の責務分担
- 各コンポーネントは、仕様書(`docs/システムフォルダ/<番号>-<名称>-仕様書.md`)の入出力契約を
  満たす関数を公開するモジュールとする。他コンポーネントは公開関数のI/O契約のみに依存し、
  内部実装(外部API呼び出し詳細等)を直接参照しない
- 105(オーケストレーター)を`src/orchestrator.py`とし、101〜104を順に呼び出すエントリポイントに
  専念させる(GitHub Actionsから`python -m src.orchestrator`等で起動する想定)
- 102(状態管理)が担う状態ファイル(`data/delivered.json`)の読み書きは102のモジュール内に閉じ込め、
  他コンポーネントは102の公開関数経由でのみアクセスする

## 3. エラー処理方針
- リカバリ可能な個別エラー(例: 個別RSSフィード取得失敗)はWARNログを出し、当該処理単位を
  スキップして継続する
- 致命的なエラー(全滅・必須の外部連携失敗等)は例外を送出する。各コンポーネントで握りつぶさず、
  105(オーケストレーター)が最終的にcatchしてERRORログを出し、プロセスを異常終了させる
  (GitHub Actions側で失敗として検知させ、不完全な状態でのLINE送信を防ぐ)
- 独自例外は薄いものに留め、コンポーネントごとに1種類程度(例: 101なら`CollectionError`)を
  基本とし、無闇に例外階層を増やさない

## 4. 運用ルール

- 新しい実装がこのファイルに記載のない領域に触れる場合、Claudeが妥当な案を1つ提示し、開発者の了承を得てから
  このファイルの該当セクションに追記する。無断で規約を確定させない
- 既存の記載内容と矛盾する実装が必要になった場合、実装せずに理由を先に説明し、規約を変更するか例外を認めるかの
  可否を確認してから進める
- 例外を認める場合も、理由を「5. 例外ログ」に1行残す

## 5. 例外ログ
(4のルールから外れた実装を行った場合、日付・箇所・理由を1行で追記する)

## 6. 決定記録(ADR)

命名規則・層分担・技術選定など、あとから「なぜこうしたか」が読み取れないと困る決定をしたら、
その直後に以下の形式で1件追記する。却下した代替案とその理由は必ず含める。事実確認が必要な箇所は
`[要確認]`と書き、推測で埋めない。

```markdown
### ADR-XXXX: [決定の要約]
- 日付:
- 背景: [この決定が必要になった背景・制約]
- 決定: [何を採用したか]
- 検討した代替案: [却下案A: 理由] [却下案B: 理由]
- 影響: [この決定によって生じる制約・将来への影響]
```

(このセクションの下に、決定のたびにADRを追記していく)

### ADR-0001: 実装言語とコンポーネント=モジュールの1:1対応
- 日付: 2026-08-19
- 背景: システム100(AI駆動開発ニュース配信システム)の実装に着手するにあたり、命名規則・
  層分担・エラー処理方針が未確定だった
- 決定: Python(PEP8/snake_case)を採用し、コンポーネント1つにつきモジュール1つを対応させる
  構成とする。致命的エラーは105(オーケストレーター)が最終catchし、失敗時はLINE送信を行わない
- 検討した代替案:
  - controller/service/repositoryの厳密な層分離: 5コンポーネント程度の個人プロジェクトには
    過剰で、仕様書のコンポーネント境界とコードのモジュール境界がずれると追跡しづらくなるため
    不採用
  - Node.js/TypeScript: GitHub Actions・LINE Messaging API・Anthropic APIいずれもPython SDKが
    公式提供されており、単一言語で完結できるPythonを優先。TypeScript化による追加の型安全性より
    構成のシンプルさを優先した
- 影響: 以降のコンポーネント(102〜105)もPythonで実装する前提となる。他言語を混在させる場合は
  この決定を先に見直す

### ADR-0002: 「6ヶ月」を暦月ではなく固定183日で近似する
- 日付: 2026-08-19
- 背景: 101(LOOKBACK_DAYS)・102(RETENTION_DAYS)ともに「直近6ヶ月」という期間条件があり、
  独立レビューで暦月と固定日数の間に数日のずれが生じる点を指摘された
- 決定: 個人の情報キャッチアップ用途では数日のずれによる実害がない(月末の記事が数日早く/遅く
  対象から外れる程度)と判断し、`dateutil`等の追加依存を導入せず固定183日の近似のままとする
- 検討した代替案: `dateutil.relativedelta`による暦月演算 → 依存関係が1つ増える割に、
  この用途では精度向上の実益が乏しいため不採用
- 影響: 6ヶ月境界付近の記事について、実際のカレンダー上の6ヶ月と数日ずれる場合がある
  (101のニュース収集・102の状態ファイル保持期間の両方に適用)
