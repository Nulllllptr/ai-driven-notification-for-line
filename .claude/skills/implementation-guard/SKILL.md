# 実装ガード

開発者は生成物の中身を確認しないものとして扱い、確認すべき点をClaudeの側から差し出す。
設計時のセキュリティ観点は`security-guard`が扱う。本スキルは実装そのものの品質・整合性を扱う。

## 1. 実装前に自分で確認すること

開発者からの指示を待たず、実装に入る前に次を判定する。

- 想定差分が200行を超えるか → 超えるなら実装せず分割案を提示する
- `implementation-rules.md`の既存規約に反するか → 反するなら実装せず理由を先に述べる
- 推測でしか埋められない仕様があるか → あるなら実装せずその箇所を挙げる

## 2. 実装と同時に必ず出力するもの

開発者が求めなくても、毎回添える。求められてから出す運用にしない。

### 2-1. 判断の根拠
なぜこの実装にしたか。検討して却下した代替案とトレードオフ。

### 2-2. 依頼範囲外の変更の申告
依頼していないのに変更・追加・削除したファイル・関数・設定を列挙する。
該当がなければ「依頼範囲外の変更なし」と明記する。省略しない。

### 2-3. 外部境界の一覧
今回の変更で追加・変更された箇所のうち、次の3種をファイル名と行番号で挙げる。

1. 外部入力が入る箇所
2. 外部に通信・書き込みする箇所
3. 認可判定をしている箇所

該当がなければ「該当なし」と明記する。

### 2-4. テスト整合の申告
次のいずれかを行った場合、必ず該当箇所を挙げる。

- テストを通すために実装側の振る舞いを変更した
- 実装の実挙動に合わせてアサーションを調整した
- テスト名と実際のアサーションが一致しない箇所が生じた

これらはテストが緑のまま成立するため、実行結果からは検知できない。申告を省略しない。

## 3. 介入の型

3行以内。作業は止めない。

エラー消しを求められた場合：
```
先に原因を特定します。[該当箇所]の[変数/戻り値]が[想定]ではなく[実際]になっています。
対処は(a)[症状を止める案] (b)[原因を直す案] の2つで、(b)を推奨します。
どちらで進めますか。
```

## 4. 実装を止める条件

以下のみ、作業を止めて確認を取る。それ以外は止めない。

- シークレットの平文混入、認可の欠落を検知したとき
- 差分が200行を超える見込みになったとき
- 同じ箇所の修正が3回連続で失敗したとき(5の撤退判断に従う)
- 依頼された仕様と`implementation-rules.md`の既存方針が矛盾するとき

## 5. 撤退判断(3回連続失敗時)

同じ箇所の修正が3回連続で失敗した時点で、修正を続けない。開発者の指示を待たずに提示する。

```
同じ箇所で3回失敗しました。ここで判断を分けます。
(a) 修正を続ける: [残っている手がかりと見込み]
(b) 破棄して分割し直す: [分割案を1行で]
[a または b]を推奨します。理由は[1行]。
```

理解できていないコードへの修正の深追いは、抜け出せない状態に落ちる典型的な経路にあたる。

## 6. 実装上の固定ルール

- 生SQLでユーザー入力値を扱う場合、必ずプレースホルダーを使う。文字列結合はしない。
- 外部入力は、型注釈ではなく実行時の検証を入れる。
- catchを空にしない。ログを残し、外部にはエラー詳細を返さない(`logging-rules`の方針に従う)。
- ループ内でクエリを発行しない。
- 手動対応が前提の実装(定期的な手作業での確認・反映等)は避け、自動化またはCI/CD(`cicd-guard`)へ
  組み込めないかを先に検討する。自動化が明らかに割に合わない場合のみ、手動対応の理由を1行添えて許容する。

## 7. エラー対応の原則

- 同じエラーを解消するために、成功するまでリトライを繰り返す・待機するといった、エラーの本質を
  迂回する手段は使わない。原因を特定し、コードの編集によって解決されるまで「対処した」とみなさない。
- 修正を行う前に、対象のコードを必ず読み直す。「なぜこの修正が正しいと言えるか」を説明できない
  修正は行わない。症状だけを見て、コードを読み直さずに直さない。

## 8. 実装後の検証

実装・改修のたびに、次を行ってから完了とする。

- 静的テスト(型チェック・lint・既存/新規のユニットテスト)を実行し、正常に動作するか確認する
- 異常値・境界値(空文字・null・0件・上限値・想定外の型等)を与えた場合の挙動も確認する
- 確認できなかった場合は「未検証」と明記し、検証済みであるかのように報告しない
