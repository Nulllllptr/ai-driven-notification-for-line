# 運用ガード

このスキルは運用の「設計パターンとチェックリスト」を扱う。特定のログ基盤・通知先を前提にした
具体スクリプトの実装はここでは行わない(対象インフラが未確定な段階での実装は投機的実装にあたるため)。
具体的な接続先・閾値は`ops-config.json`等の外部ファイルに定義し、プロジェクト側で用意する。

## 1. 最低限決めるべきこと(チェックリスト)

- 監視対象は何か(エラー率、レイテンシ、特定のログパターン等)
- 異常とみなす条件(閾値・連続回数)は何か
- 検知した後、誰/何に通知するか
- 対応のうちどこまでを自動化してよいか(下記2で必ず範囲を分ける)

いずれかが未確定のまま実装に入ろうとしている場合、実装せずこの4点を先に確認する。

## 2. ログ起点のLLM自動修正ループ(設計パターン)

```
ログ収集 → 異常検知(閾値/パターンマッチ) → LLMへ原因推定・修正案の生成を依頼
  → 修正案の適用範囲を判定 → [自動適用 or 人間レビュー] → デプロイ → 効果確認 → ログ収集に戻る
```

- 自動適用してよい範囲は、設定値の調整など影響範囲が限定的なものに限る。コード変更・権限変更・
  データ削除を伴う修正は既定で人間レビュー必須とする。範囲を広げる場合は開発者の明示的な合意を得る
- 修正案の生成・適用ログ自体も`logging-rules`の方針に従って記録し、後から誰が/何が何を変更したか追跡できるようにする
- 自動修正が同じ箇所を繰り返し変更する場合は自動適用を止め、人間の判断を挟む

## 3. 導入時の確認

該当システムのシステム単位設計書(docs/システムフォルダ/配下)「5. 制約・前提」にコンプライアンス要件がある場合、自動適用の範囲がそれに抵触しないか
`security-guard`の観点と合わせて確認する。
