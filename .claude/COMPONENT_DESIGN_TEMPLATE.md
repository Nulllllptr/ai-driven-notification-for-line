# コンポーネント設計書: <コンポーネント名>

このコンポーネントが属するシステムは`./<システム番号>-システム仕様書.md`を参照。
対応するテスト成果物は`./<番号>-<コンポーネント名>-テスト.md`。

## 1. 目的
このコンポーネントが担う役割を1〜2行で。

## 2. 説明
何をするコンポーネントか、なぜ必要か。他コンポーネントとの分担境界を含める。

## 3. 入力
受け取るデータ・イベントの形式とソース(呼び出し元コンポーネント、外部API、キュー等)。
未確定の間は「未確定」と明記する。仕様が固まらない論点は推測で埋めず、開発者に確認してから埋める。

## 4. 出力
返す・送るデータの形式と宛先(呼び出し元、外部API、データストア等)。
未確定の間は「未確定」と明記する。仕様が固まらない論点は推測で埋めず、開発者に確認してから埋める。

## 5. 依存コンポーネント・外部連携
このコンポーネントが依存する他コンポーネント・外部サービスを列挙する。

## 6. 制約・注意事項
性能要件、既知の制限、変更時に壊れやすい箇所など。非機能要件テストの基準はここに書く
(component-test-guardが「6. 制約・注意事項」を根拠に非機能要件テストを実施する)。

## 7. 受け入れ条件(EARS形式)
自然文の箇条書きで済ませず、次の5パターンに当てはめて書く(詳細はdesign-doc-guardの2-2)。
component-test-guardの機能要件テストは、この表のIDと対応付けて実施する。

| ID | パターン | 記述 |
|---|---|---|
| AC-1 | ユビキタス/イベント駆動/状態駆動/不具合対応/オプション機能のいずれか | |

- ユビキタス: 「<コンポーネント>は<応答>する」(常に成り立つ性質)
- イベント駆動: 「<トリガー>のとき、<コンポーネント>は<応答>する」
- 状態駆動: 「<状態>の間、<コンポーネント>は<応答>する」
- 不具合対応: 「<不正な入力・状況>の場合、<コンポーネント>は<応答>する」
- オプション機能: 「<機能>を含む場合、<コンポーネント>は<応答>する」
