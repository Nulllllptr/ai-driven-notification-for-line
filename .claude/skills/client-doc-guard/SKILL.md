# 顧客向け資料ガード

## 1. 作成方針

- 技術用語は避けるか、初出時に一言で言い換える(例:「API」→「システム同士がやり取りする窓口」)
- 実装の手段より、利用者にとっての変化(何ができるようになる/変わるか)を先に書く
- コードスニペット・内部ファイルパス・内部設計上の理由は含めない

## 2. 標準フォーマット

1. **概要**: 何をしたか(1〜2行)
2. **背景・目的**: なぜ行ったか、何が課題だったか
3. **利用者への影響**: 何が変わるか。変わらない点も明記する(過剰な期待を避けるため)
4. **適用時期**: いつから反映されるか

## 3. 含めてはいけない情報

- コスト内訳・原価などの内部情報(`cost-guard`で扱った内容)
- 発見したセキュリティ上の欠陥の具体的な手口(`security-guard`で扱った内容)。対応済みである旨のみ記載する
- 個人用の開発ルール・ガードレールの内容(CLAUDE.md等)

## 4. 出力後の確認

作成した資料を提示する際、「内部情報が含まれていないか」を1行で自己点検してから開発者に渡す。

## 5. 品質・セキュリティへの取り組みの説明(CLIENT_TRUST_OVERVIEW.md)

「どのような考えで開発しているか」を顧客に説明する資料は、標準フォーマット(2)ではなく
`CLIENT_TRUST_OVERVIEW_TEMPLATE.md`をコピーした`CLIENT_TRUST_OVERVIEW.md`を使う。

- `docs/BIRDSEYE_DESIGN.md`「5. 開発方針」表で有効なユニットの節だけを残し、無効なユニットの節は削除する
- 内容が実装と乖離していないか、`design-doc-guard`の更新タイミングに合わせて見直す
