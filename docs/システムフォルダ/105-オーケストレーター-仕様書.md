# コンポーネント設計書: オーケストレーター

このコンポーネントが属するシステムは`./100-システム仕様書.md`を参照。
対応するテスト成果物は`./105-オーケストレーター-テスト.md`。

## 改訂履歴
- 2026-08-19: 当初「記事が3件未満の日はLINE送信をスキップする」想定でヒアリングしたが、
  開発者の指示により「3件未満でも(1〜2件でも)送信する」方針に変更した。0件の場合のみ
  送信を行わない(104自身のAC-2による安全策と重複する形になるが、105としても明示的に
  スキップを判断する)。

## 1. 目的
101(ニュース収集)→102(重複判定・状態管理)→103(記事要約・生成)→104(LINE配信)を順に呼び出し、
配信成功後に102へ配信記録を残す。GitHub Actionsのscheduled workflowから毎日9:00 JSTに起動される
エントリポイント。

## 2. 説明
`python -m src.orchestrator`として実行可能なスクリプト。各コンポーネントの公開関数を順に呼び出し、
いずれかが例外を送出した場合はエラーログを出して異常終了する(`implementation-rules.md`3節の
エラー処理方針に基づく、105による最終catch)。

`data/delivered.json`のコミット&push自体はこのスクリプトの責務ではなく、GitHub Actions
workflow(`.github/workflows/daily-news.yml`)側のステップとして行う(Pythonはビジネスロジックに
専念し、Git操作はCIのステップに委ねる層分担)。

## 3. 入力
- コマンドライン引数・関数引数: なし(スクリプトとして実行)
- 環境変数: `LINE_CHANNEL_ACCESS_TOKEN`・`LINE_USER_ID`・`ANTHROPIC_API_KEY`(101〜104が
  内部で参照する。105自身が直接参照するものはない)

## 4. 出力
- 標準出力: 構造化ログ(logging-rules.md準拠)
- 終了コード: 成功時0、いずれかのコンポーネントが例外を送出した場合は1
- 副作用: 記事が1件以上生成された場合、`data/delivered.json`が更新される(102経由)

## 5. 依存コンポーネント・外部連携
- 依存コンポーネント: 101・102・103・104(すべて呼び出す)
- 外部連携: なし(各コンポーネントが個別に外部連携を持つ)

## 6. 制約・注意事項
- LINE配信が成功した後に102への状態記録(`record_delivered`)が失敗した場合(状態ファイル破損等)、
  オーケストレーターはエラーとして異常終了する。この場合、次回実行時に同じ記事が未配信として
  再び候補になり得る(重複配信のリスクより、状態ファイル破損を隠さないことを優先する102の
  設計判断を踏襲する、既知の制約)
- 101〜104のいずれかが失敗した場合、後続のコンポーネントは呼び出さない(部分的な配信を防ぐ)
- 「記事が3件未満でも送信する」(開発者の明示的な指示、改訂履歴参照)。0件の場合のみ
  LINE配信(104)を呼び出さない

## 7. 受け入れ条件(EARS形式)

| ID | パターン | 記述 |
|---|---|---|
| AC-1 | ユビキタス | オーケストレーターは101→102→103の順に呼び出し、生成された記事が1件以上あれば104を呼び出してLINE配信する |
| AC-2 | イベント駆動 | 103が生成した記事が0件のとき、オーケストレーターは104を呼び出さずに正常終了する |
| AC-3 | イベント駆動 | LINE配信が成功したとき、オーケストレーターは配信した記事(url・title)を102(`record_delivered`)へ記録する |
| AC-4 | 不具合対応 | 101・102・103・104のいずれかが例外を送出したとき、オーケストレーターはエラーログを出力し、後続のコンポーネントを呼び出さずに終了コード1で終了する |
| AC-5 | 不具合対応 | LINE配信が成功した後に102への状態記録が失敗した場合、オーケストレーターはエラーログを出力し終了コード1で終了する |
