# 設計書ガード

## 0. 3階層の役割

鳥瞰図設計書は`PRODUCT.md`/`TECH.md`/`STRUCTURE.md`の3ファイルで構成する。「層」としては
プロジェクト全体を1つの単位として扱う点は変わらない。

| 階層 | 対象範囲 | テンプレート | 生成先 |
|---|---|---|---|
| 鳥瞰図設計書(プロダクト) | プロジェクトの目的・対象ユーザー・提供価値 | `PRODUCT_TEMPLATE.md` | `docs/PRODUCT.md` |
| 鳥瞰図設計書(技術) | インフラ構成・技術スタック・開発方針(有効ユニット) | `TECH_TEMPLATE.md` | `docs/TECH.md` |
| 鳥瞰図設計書(構造) | ディレクトリ構成・稼働システム一覧・大まかなIN→OUT | `STRUCTURE_TEMPLATE.md` | `docs/STRUCTURE.md` |
| システム単位設計書 | 1システムの目的・意図・コンポーネントのつながり・依存関係・IN→OUT処理フロー | `SYSTEM_DESIGN_TEMPLATE.md` | `docs/システムフォルダ/<番号>-システム仕様書.md`(システム1つにつき1ファイル) |
| コンポーネント単位設計書 | 1コンポーネントの目的・説明・入出力形式・EARS形式の受け入れ条件 | `COMPONENT_DESIGN_TEMPLATE.md` | `docs/システムフォルダ/<番号>-<コンポーネント名>-仕様書.md`(コンポーネント1つにつき1ファイル) |

採番台帳は`docs/システムフォルダ/README.md`(`SYSTEM_INDEX_TEMPLATE.md`から生成)。
5ファイル(PRODUCT/TECH/STRUCTURE+システム単位+コンポーネント単位)は必ずセットで揃える。
1つだけ作って終わらせない。

**最優先原則: 仕様書は常に必須。** コンポーネントの実装・修正は、対応するコンポーネント単位設計書
なしには行わない。この原則は`dev-method-guard`の開発手法選択(TDD/仕様書駆動/特に定めない)より
優先する。詳細は4節。

## 1. 起動条件の確認

- `docs/PRODUCT.md`・`docs/TECH.md`・`docs/STRUCTURE.md`のいずれか、またはシステム単位設計書が
  存在しない → 2へ(新規生成)
- 開発者からコンポーネントの実装・修正の指示が来た → 先に4節のゲートを通す
- 全て存在し、指示もない → 直近の実装変更と突き合わせ、コンポーネント構成・処理フロー・
  インフラ構成が乖離していないか確認する。乖離があれば5へ。なければ内容を読み込んで作業に入ってよい

## 2. 新規生成時のヒアリング(目的・制約・有効ユニットのみ)

対象がスクラッチ開発(まだコードが存在しない)か既存コードへの導入かをまず確認する。
既存コードへの導入であれば、ヒアリングの前にコードとインフラ設定を読み、聞かずに読み取った内容で埋める
(`docs/TECH.md`の技術スタック・`docs/STRUCTURE.md`のディレクトリ構成はこの読解だけで埋まることが多い)。

スクラッチ開発の場合、コンポーネントのつながり・処理フロー・インフラ構成は何も存在しないため聞かない。
次の項目だけを聞く。

```
設計書を作成します。分かる範囲で構いません。埋まらない項目は「未確認」のままにします。
1. このプロジェクト全体は何のためのものですか(誰の・どんな課題を解決するか)
2. このプロジェクトで有効化する開発ルール(dev-method-guard等、テンプレート内のユニット)はどれですか
3. 負荷想定・コスト上限・コンプライアンス等、設計判断に影響する制約はありますか
```

回答が一部だけでも、その範囲で3へ進む。空欄は「未確認」と明記し、Claudeが推測で埋めない。
コンポーネント単位設計書は、対象コンポーネントの実装依頼が来た時点(4節のゲート)で生成する
(スクラッチ開始時点では対象コンポーネントが存在しないため先に作らない)。

### 2-1. 採番規則
- システム: 100刻み(100, 200, 300…)。`docs/システムフォルダ/README.md`で空いている最小の
  100の倍数を確認して割り当てる
- コンポーネント: 所属システム番号+1から連番(システム100番なら101, 102…)
- 番号を割り当てたら、仕様書ファイルを作る前に採番台帳へ先に追記する

### 2-2. EARS形式の受け入れ条件
コンポーネント単位設計書の受け入れ条件は、次の5パターン(EARS記法)のいずれかで書く。
自然文の箇条書きで済ませず、パターンに当てはめて曖昧さを減らす。

| パターン | 構文 | 使う場面 |
|---|---|---|
| ユビキタス | 「<コンポーネント>は<応答>する」 | 常に成り立つ性質 |
| イベント駆動 | 「<トリガー>のとき、<コンポーネント>は<応答>する」 | 入力・イベントへの反応 |
| 状態駆動 | 「<状態>の間、<コンポーネント>は<応答>する」 | 状態に応じた継続的な振る舞い |
| 不具合対応 | 「<不正な入力・状況>の場合、<コンポーネント>は<応答>する」 | 異常系・エラー処理 |
| オプション機能 | 「<機能>を含む場合、<コンポーネント>は<応答>する」 | 一部構成でのみ有効な要件 |

## 3. 生成・更新

- `PRODUCT_TEMPLATE.md`/`TECH_TEMPLATE.md`/`STRUCTURE_TEMPLATE.md`をそれぞれコピーし
  `docs/PRODUCT.md`/`docs/TECH.md`/`docs/STRUCTURE.md`として生成(既存の場合は差分のみ更新)
- `SYSTEM_DESIGN_TEMPLATE.md`をコピーし`docs/システムフォルダ/<番号>-システム仕様書.md`として生成
- `COMPONENT_DESIGN_TEMPLATE.md`をコピーし`docs/システムフォルダ/<番号>-<コンポーネント名>-仕様書.md`
  として生成(4節のゲートに従う。受け入れ条件は2-2のEARS形式で書く)
- `SYSTEM_INDEX_TEMPLATE.md`をコピーし`docs/システムフォルダ/README.md`として生成。採番のたびに追記
- 「開発方針」の表(`docs/TECH.md`側、プロジェクトで1つ)は、CLAUDE.mdのユニット索引と
  突き合わせ、実際に導入済みのものだけ「有効」にする
- 生成後、変更点を3行以内で要約して開発者に提示する

## 4. 仕様書必須化(実装前のハードゲート)

開発者からコンポーネントの実装・修正の指示が来たら、実装に入る前に必ず次を確認する。

- 該当コンポーネントの仕様書(`docs/システムフォルダ/<番号>-<コンポーネント名>-仕様書.md`)が
  存在するか確認する
- **存在しない**(新規コンポーネント、または仕様書が作られる前に実装だけを指示された)
  → 実装せず、先に仕様書を作成する。2-1の採番規則で番号を割り当て、`COMPONENT_DESIGN_TEMPLATE.md`
  の1(目的)〜7(受け入れ条件)を埋める。入出力の形式・依存関係・エラー時の扱いなど、仕様として
  確定させる必要がある論点が残っている場合は、実装に入らずその場で開発者に確認してから確定させる。
  推測で仕様を埋めない
- 仕様書の内容について開発者の同意を得てから実装に入る
- **存在する**(既存コンポーネントの修正) → 実装前に仕様書を読み、依頼内容と矛盾しないか確認して
  から実装に入る

この優先順位は`dev-method-guard`の開発手法選択(TDD/仕様書駆動/特に定めない)より上位に置く。
「特に定めない」を選んでいても、コンポーネント仕様書の作成義務は免除されない(詳細は
`dev-method-guard`の1節)。実装後は`component-test-guard`による単体実行確認に進む。

開発者から実装指示・確認・相談があった場合、上記に加えて次の設計書も参照してから回答する。
読まずに回答しない。
- システム内の連携・処理フローに関わる相談 → システム単位設計書
- システム間連携・インフラ・技術方針に関わる相談 → 鳥瞰図設計書(PRODUCT/TECH/STRUCTUREのうち該当するもの)

## 5. 実装・修正後の追従(更新義務)

次の変更が生じたとき、該当する設計書を必ず更新する。ヒアリングでは埋めない
(推測や事前申告ではなく実装結果を反映する)。

- コンポーネントの入出力・責務変更 → コンポーネント単位設計書(実装直後、component-test-guardの
  テスト実行より前に更新する)
- コンポーネントの追加・削除・依存関係の変更 → システム単位設計書とコンポーネント単位設計書、採番台帳
- システム間連携・インフラ構成の変更 → `docs/STRUCTURE.md`・`docs/TECH.md`
- 処理フロー(入力から出力までの経路)の変更 → 該当する階層の設計書

更新のたびに、根拠にしたファイルを1行で示す(例: 「package.jsonの依存関係から技術スタックを更新」)。

## 6. 3階層間の整合性

生成・更新のたびに次を確認する。

- `docs/STRUCTURE.md`の「稼働システム一覧」と、実在するシステム単位設計書が一致しているか
- システム単位設計書の「コンポーネントのつながり」表と、同フォルダ内の実ファイルが一致しているか
- コンポーネントの依存関係に循環がないか(AがBに依存し、BがAにも依存する、のような閉路がないか)
- 採番台帳(`docs/システムフォルダ/README.md`)と実ファイルの番号が一致しているか

不一致があれば、実装せず不一致点を指摘してから進める。

## 7. 以降の会話での扱い

- 同一セッション内で既に設計書を読み込み済みの場合、再読み込みは不要。ただし新しいセッションの
  最初の応答では必ず読み直す
- 内容と矛盾する実装依頼が来た場合、実装せず矛盾点を指摘してから進める
