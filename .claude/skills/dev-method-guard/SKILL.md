# 開発手法ガード

本スキルが決めるのは「テストを先に書くか後に書くか」という順序のみ。コンポーネント仕様書
(コンポーネント単位設計書)自体の作成義務は`design-doc-guard`が手法選択と関係なく常に課す。
「特に定めない」を選んでも仕様書の作成は免除されない(1節)。

## 1. 採用手法の確認

`docs/TECH.md`の「5. 開発方針」表、`dev-method-guard`行の補足欄を読む。

- 値がある(例: TDD / 仕様書駆動) → 2の該当手順に従う
- 「未確認」または欄が空 → 実装せず、次を1回だけ聞く。「このプロジェクトの開発手法は TDD / 仕様書駆動 / 特に定めない のどれにしますか」。回答を得たら`docs/TECH.md`の該当欄に書き戻してから2へ進む
- 「特に定めない」が明示されている → 本スキルの手順(テストを先に書くか後に書くか)は適用せず、
  通常の実装ルール(implementation-rules等)にのみ従う。ただしコンポーネント仕様書の作成義務は
  `design-doc-guard`が別途課すため免除されない

## 2. 手法ごとの手順

### 2-1. TDDの場合
1. 対象コンポーネントの仕様書(design-doc-guardの4節を通過済みのもの)を読み、受け入れ条件を1文で確認する
2. 失敗するテストを先に書く
3. テストが実際に失敗することを確認してから実装に入る
4. 実装後、テストが通ることを確認する。通らない場合は実装を直す(テスト側を実挙動に合わせて調整した場合は、CLAUDE.mdの申告ルールに従いその旨を明示する)
5. `component-test-guard`で条件網羅・機能要件・非機能要件のテストを実施する

### 2-2. 仕様書駆動の場合
1. 対象コンポーネントの仕様書(`docs/システムフォルダ/<番号>-<コンポーネント名>-仕様書.md`)を
   `design-doc-guard`の4節に従って作成・確認する。この仕様書がそのままテスト設計の起点になるため、
   `docs/specs/`等の別ファイルを重複して作らない
2. 仕様書の内容について開発者の確認を得てから実装に入る
3. 実装後、仕様書と実装が一致しているか突き合わせる。差異があれば仕様書側を先に直すか実装側を直すか開発者に確認する
4. `component-test-guard`で条件網羅・機能要件・非機能要件のテストを実施する

## 3. 手法の変更

開発者が途中で手法を変更したいと明示した場合、`docs/TECH.md`の該当欄を更新し、以後は新しい手法の手順に従う。過去に作ったテスト・仕様書の遡及的な作り直しは、明示的な依頼がない限り行わない。
