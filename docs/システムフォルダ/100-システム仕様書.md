# システム単位設計書: AI駆動開発ニュース配信システム

開発方針(有効ユニット)はプロジェクト全体で共通のため、`../TECH.md`「5. 開発方針」を参照する。

## 1. 目的・意図
AI駆動開発(手法・ツールの動向、および要件定義/レビュー人材需要の変化など市場動向)に関する
直近6ヶ月程度の最新情報を毎朝9:00に自動収集し、3件の記事にまとめてLINEへ通知する。
一度取り上げた情報・類似記事は再配信しない。全体での位置づけは`../PRODUCT.md`を参照。

## 2. コンポーネントのつながり(実装に追従して更新)

| 番号 | コンポーネント名 | 役割(1行) | 依存コンポーネント | 並列実装可否 | コンポーネント設計書 |
|---|---|---|---|---|---|
| 101 | ニュース収集 | RSS/フィードから直近6ヶ月のAI駆動開発関連候補記事を取得する | なし | 可 | ./101-ニュース収集-仕様書.md |
| 102 | 重複判定・状態管理 | 配信済み記事(URL・トピック指紋)を記録し、候補から既配信分を除外する | なし | 可 | ./102-重複判定状態管理-仕様書.md |
| 103 | 記事要約・生成 | 101の候補から102未配信のものを対象に、LLMで3件の記事へ要約する | 101, 102 | 不可(101・102完了待ち) | ./103-記事要約生成-仕様書.md |
| 104 | LINE配信 | 103が生成した3件の記事をLINE Messaging APIでプッシュ送信する | 103 | 不可(103完了待ち) | ./104-LINE配信-仕様書.md |
| 105 | オーケストレーター | GitHub Actionsのスケジュール実行から101→102→103→104を順に呼び出し、配信成功後に102の状態を更新・コミットする | 101, 102, 103, 104 | 不可(全コンポーネント完了待ち) | ./105-オーケストレーター-仕様書.md |

## 3. 入力から出力までの処理フロー(実装に追従して更新)
1. GitHub Actionsが毎日9:05 JST(0:05 UTC)頃に105を起動する
2. 105が101を呼び出し、RSS/フィードから直近6ヶ月のAI駆動開発関連候補記事一覧を取得する
3. 105が102を呼び出し、101の候補から配信済み(URL一致・類似トピック)を除外する
4. 105が103を呼び出し、残った候補からLLMで3件の記事(手法動向・市場動向を含む)を生成する
5. 105が104を呼び出し、3件の記事をLINEへプッシュ送信する
6. 送信成功後、105が102に配信済み記事(URL・トピック指紋・配信日)の記録を追加させ、
   リポジトリへコミットする

## 5. 制約・前提
- コスト: LINE Messaging APIは月200通まで無料(1日1通のため十分収まる見込み)。
  Anthropic API(要約用途)は従量課金だが、月数百円程度は許容する方針(開発者了承済み)
- 実行環境: ローカル実行は行わない。GitHub Actionsのscheduled workflowのみで完結させる
- 負荷想定: 1日1回・記事3件程度の小規模バッチ処理。高頻度・大量処理は想定しない
- 対象情報: 直近6ヶ月程度のAI駆動開発関連情報(手法・ツール動向、要件定義/レビュー人材需要
  等の市場動向を含む)。日本語ソースに加え英語ソースも収集対象に含める
- LINE公式アカウント: 未作成(開発者がLINE Developersコンソールで作成する。104の実装時に
  手順を案内する)
- コンプライアンス: 個人利用のため対象外。ただし収集元の利用規約・著作権(記事本文の丸ごと
  転載は避け、要約に留める)には注意する

## 6. 用語集
- トピック指紋: 記事の見出し・本文から算出する類似度判定用の特徴量。URLが異なっていても
  同一トピックの記事を「既出」として除外するために102が用いる(具体的な算出方式は102の
  仕様書で確定する)
