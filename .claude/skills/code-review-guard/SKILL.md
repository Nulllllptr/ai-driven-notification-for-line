# コードレビューガード

開発者からレビュー依頼が来るのを待たない。Claudeが先に見て、結果を出してから確認を求める。

## 1. release-review-guardとの使い分け

| | code-review-guard(本スキル) | release-review-guard |
|---|---|---|
| タイミング | 依頼時・実装完了報告時。随時 | コミット/マージ/デプロイ/リリース直前のみ |
| 主眼 | 正確性バグ・重複/簡潔化/効率 | シークレット・認可を最優先とした事故防止 |
| セキュリティ観点 | 明らかな不備があれば指摘するが深追いしない | 本命。Critical/Highを最優先で潰す |

同一差分に両方が該当する場合(実装完了報告のままコミットする等)、本スキルを先に通してから
release-review-guardのCritical2点確認に進む。

## 2. 見る観点と順番

| 順 | 観点 | 見る内容 |
|---|---|---|
| 1 | 正確性 | ロジック誤り、境界値・null・例外の未処理、意図と実装のズレ |
| 2 | 重複 | 同等の処理が複数箇所に存在しないか。既存の共通処理を使えないか |
| 3 | 簡潔化 | 不要な抽象化・過剰な分岐・使われていない引数や分岐 |
| 4 | 効率 | 不要なループ内クエリ・計算量が明らかに悪い実装 |

差分を上から順に読まない。見るのは「どこが壊れるか・どこが無駄か」。

## 3. 指摘の出し方

指摘は必ず次の3点をセットで書く。1つでも欠けたら、開発者は手を動かせない。

- どこが(ファイル名:行番号)
- 何が問題か
- どう直すか

分類はrelease-review-guardと共通の4段階。

| 分類 | 基準 |
|---|---|
| Critical | 実行時に確実に壊れる、または致命的なデータ不整合を招く |
| High | 特定条件下でバグとして顕在化する |
| Medium | 重複・簡潔化で明確に改善できる |
| Low | 効率・命名など、時間があるとき |

該当なしの観点は「該当なし」と明記する。対応不要な指摘には「対応不要」と併記してよい。

## 4. 繰り返さない条件

- Critical / High が0件の場合、介入は1回のみ。同じ指摘を繰り返さない。
- 開発者が「承知の上で進める」と答えたら、その件はそのセッション中は二度と指摘しない。
