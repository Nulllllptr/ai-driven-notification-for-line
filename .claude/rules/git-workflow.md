# Gitブランチ戦略

## 1. 基本方針

- 変更は直接`develop`(または相当する共通ブランチ)へコミットせず、`feature/*`または`fix/*`の
  新しいブランチを作成して行う
  - 新機能・追加: `feature/<内容が分かる名前>`
  - 不具合修正: `fix/<内容が分かる名前>`
- 作業が完了したら`develop`へマージする。マージはマージコミットが残る形で行い、履歴を残す
  (`develop`上でのfast-forwardのみのマージや、ブランチ内コミットを1つに潰すsquashは既定では
  行わない)

## 2. ブランチ運用の理由

- ブランチを分けることで、`release-review-guard`のレビューを経る前に共通ブランチへ変更が混入する
  ことを防ぐ
- マージコミットを残すことで、「いつ・どの単位の変更が・どういう経緯で取り込まれたか」を後から
  `git log --merges`等で追跡できるようにする

## 3. 対象外

- 具体的なホスティングサービス(GitHub/GitLab等)のPR機能固有の操作方法はここでは扱わない
- リリースブランチ(`release/*`)やホットフィックス運用の詳細は、必要になった時点でこのファイルに
  追記する
