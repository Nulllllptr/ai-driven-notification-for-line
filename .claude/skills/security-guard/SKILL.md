# セキュリティガード

## 1. チェック観点(具体項目)

実装提案の直前に、対象の変更が下記の各項目に該当するかを確認する。該当する項目だけ1行で対応方針を書く。
該当しない項目は列挙しない(全項目を毎回書き出して水増ししない)。

- **認可**: この機能を呼び出せるのは誰か。権限チェックのコードがどこにあるか
- **入力検証**: 外部由来の値(ユーザー入力・API応答・ファイル・環境変数)をどこで検証しているか
- **シークレット**: APIキー・パスワード・トークンを平文でコード/ログ/コミットに含めていないか
- **通信**: 外部通信が暗号化されているか。証明書検証やホスト名検証を無効化していないか
- **依存関係**: 新規に追加する外部ライブラリ・パッケージに既知の脆弱性報告がないか(確認できない場合は「未確認」と明記する)
- **最小権限**: 付与するロール・スコープ・ファイルアクセス権が必要最小限か
- **機微情報のログ混入**: `logging-rules`が有効な場合、そちらの禁止項目と重複がないか突き合わせる

## 2. 該当なしの扱い

上記のどの項目にも該当しない変更(表示文言の修正等)であれば、「セキュリティ観点: 該当なし」と1行で述べて次に進む。省略しない。

## 3. 見つかった場合の扱い

- 修正コストが小さい指摘は、実装提案に組み込んで一緒に提示する
- 設計判断が必要な指摘(例: 認可方式の選定)は、実装せずに先に開発者へ確認する
- 既に本番稼働中のコードに重大な欠陥(シークレット平文混入・認可欠落)を見つけた場合は、修正を進めず作業を止め、
  発見内容を開発者に報告してから対応方針を確認する(`implementation-guard`の停止条件と同じ扱いとする)
